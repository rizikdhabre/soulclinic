# Monthly schedule revision implementation plan

> Use subagent-driven-development, isolated tests and local main. User directly authorized these changes. No commit, push, live DB or environment access.

**Goal:** Simplify the separate monthly editor: replace by default, block instead of add/remove rows, load persisted month state, reject all writes on appointment conflicts, and keep the viewport stable.
**Architecture:** Extend existing month preview/apply service with an authenticated month-state read and appointment-conflict validation. Frontend hydrates from actual saved day schedules and keeps persistent preview geometry after save. Existing daily calendar refreshes through the success event.
**Stack:** Existing JS/JSX/Next/React/Tailwind/Mongo; no dependencies.
**Spec:** Latest user request in this conversation supersedes preservation policy and allowing edits over booked starts in the first plan.

**Subsequent UI cleanup:** The owner removed the visible saved-month section and group-delete buttons, and requested a heading arrow to collapse/expand the planner. Saved-state loading/hydration remains; the collapsed content stays mounted to preserve drafts and previews. Empty groups are ignored during preview/apply, with at least one selected weekday required overall and original group numbers retained in the preview. This supersedes the visible date-list requirement below. Current behavior is in `MONTHLY_SCHEDULE_PLANNER.md`.

## Constraints and contracts

- Old `MonthlyBlocker.jsx` and `api/appointments/block-month/route.js` remain byte-identical (hashes in original plan).
- Remove preservation dropdown and server preservation behavior. All selected eligible dates replace their schedule arrays; past/excluded/invalid dates still skip. Ignore/remove legacy customizedDays request option; canonical new intent does not include it.
- Remove add-time and delete-time controls and logic. Existing time rows remain editable; one lock button toggles blocking, blocked row has red background and button uses filled primary/green locked icon like user's image. Full closure keeps visible rows, marks every start blocked/red and saves mode closed.
- Stored legacy schedules may have fewer/more starts than defaults. Read effective arrays accurately; no time deletions by UI. For legacy omitted default starts, display those missing starts as blocked rows (do not silently open them). New rows cannot be added by user. Preserve edited-time identity through sorted stored lists; do not add missing defaults to already full edited schedules merely because times moved.
- Add authenticated GET `/api/admin/monthly-schedule/state?month=YYYY-MM`. Response `{month, days:[{date,weekday,times,blockedTimes,appointmentTimes,valid,customized}]}` for EVERY date including defaults. appointmentTimes unique HH:mm only; no PII. `times` are current effective offered starts. Backend read-only, no-store incl auth failures, validation before database access. Malformed/duplicate day valid=false. Changes from other calendar routes must appear in state, no stale configuration-only collection.
- Frontend month state visible independently of preview, with date-level status/details. Hydrate a group's rows from saved state when selecting its first weekday; use earliest relevant date as reference (today/future first), clearly label reference date and warn when matching dates differ. Adding weekdays to same group intentionally shares its current template. On first month load, show a saved customized reference where available (otherwise defaults) without auto-selecting apply weekdays. On reload/revisit month same saved changes appear. Async stale month responses ignored, load failure disables preview/apply (no fake default success); retry available. No preservation dropdown.
- New conflict rule: on apply candidate days, reject editing away or blocking an existing booked start, and reject full closure when appointments exist. Do not fail merely because unchanged booked starts remain in an otherwise compatible schedule. Existing block flags are replaceable; they are not booking conflicts. Exact-start semantics remain, not duration intervals. On conflict nothing changes, including receipt. Keep transaction/stale/idempotency guarantees.
- Preview remains HTTP200 with `conflicts:[{date,time}]`, `canApply:boolean`; summary affectedAppointments identifies conflicts. Apply returns 409 `APPOINTMENT_CONFLICT` with safe Arabic message and conflicts array. Check conflicts inside transaction BEFORE preview-token mismatch so a newly conflicting booking reports the useful conflict (unrelated changes still SCHEDULE_CHANGED). No PII. Preview/apply frontend show Arabic date/time conflicts below controls and disable apply for known conflicts; server handles races. Mark conflict as definitive failure for uncertain retries, because receipt lookup is still first.
- Success keeps preview mounted as a receipt (disable repeat apply), refresh month saved state without replacing live groups, dispatch appointments:changed with `{month, appliedDates}` detail. Keep x/y viewport stable: no preview removal/scrollIntoView, reserved feedback space, restore captured position after render only if user has not deliberately scrolled while waiting. No page reload. Error paths similarly must not jump.
